# GooseLee: три улучшения по мотивам Gristmill

Дата: 2026-10-15.
Статус: GM01–GM03 реализованы. Полный Swift-набор после исправлений независимого ревью: 1653 теста в 164 наборах, успешно.
Публикация и доставка обновлений: только GitHub Actions → GitHub Release → Sparkle. Локальная сборка или установка не подтверждает выпуск.
Основа проверки: GooseLee `9d7bcb6b`, Gristmill `bbae52baa6b2b643740536a4a60f7a3f87cbb65e`.
Пункты «Уже есть у нас» ниже описывают исходную базу до реализации. Качество на реальных встречах и ответы внешних LLM этим тестовым прогоном не подтверждены.

## Цель и границы

Добавить три возможности:

1. Задавать вопросы по архиву встреч и открывать источники ответа.
2. Видеть, чем и из каких данных получен текущий результат, и повторять нужную обработку без потери сохранённого результата.
3. Видеть происхождение имени говорящего, исправлять его и понимать, когда после исправления устарел summary.

Использовать существующие локальное хранилище, поиск, LLM-провайдеры, повторное распознавание, экран встречи и Google Meet bridge. Аудиозахват, модели ASR и нейросетевое эхоподавление не перестраивать.

В этот объём не входят векторная БД, embeddings, новый сервер, агентный фреймворк, BB-интеграция, новые ASR-провайдеры, новые платформы звонков, голосовая биометрия, WER-бенчмарки, универсальная очередь заданий и интерфейс восстановления любой исторической версии.

Это отдельное ТЗ. Оно не утверждает и не расширяет задачи из существующего `GOOSELEE_IMPROVEMENTS_SPEC.md`.

## GM01. Чат по архиву с источниками

### Уже есть у нас

- `DictationStore.searchMeetings(query:limit:)` ищет по названию, расшифровке, summary, ручным заметкам и участникам; удалённые встречи исключены.
- `SearchResultsView` показывает найденные встречи, `showMeetingDocument(id:)` открывает документ.
- `MeetingSummaryClient` поддерживает выбранный LLM-backend, ограничения ожидания и обработку ошибок. `MeetingQuickActionModel` показывает пример отмены запроса и защиты от устаревшего ответа.
- Сохранены расшифровка, summary, ручные заметки, дата и идентификатор встречи.
- Есть переход от таймкода к аудио. У него уже есть ограничения: например, для возобновлённых встреч без карты частей и после несовместимого изменения часового пояса.

Полноценного чата по нескольким встречам и адресуемых ссылок на текстовые фрагменты в проверенном коде нет.

### Что берём у Gristmill

Пользовательский сценарий общего чата: найти нужные заметки, прочитать релевантные данные, ответить по ним. Архив не отправляется модели целиком. Заимствуем идею работы с заметками; проверяемые ссылки на отдельные фрагменты — требование GooseLee, а не подтверждённая здесь возможность Gristmill.

Источники Gristmill:
- [Chat](https://github.com/timurkhakhalev/gristmill/blob/bbae52baa6b2b643740536a4a60f7a3f87cbb65e/.memory-bank/architecture/chat.md).
- [searchNotesTool.ts](https://github.com/timurkhakhalev/gristmill/blob/bbae52baa6b2b643740536a4a60f7a3f87cbb65e/src/services/tools/searchNotesTool.ts).

### Добавить: поведение

1. На экране встреч добавить действие «Спросить по встречам». Из документа встречи открывать тот же интерфейс с областью «Эта встреча».
2. В архивном режиме дать область поиска: все сохранённые встречи, текущая папка, диапазон дат. Режим одной встречи строго ограничен её ID. Даты относятся к началу встречи; границы дней вычисляются в текущем часовом поясе.
3. Показывать выбранный LLM-backend и область поиска. Использовать текущие настройки summary; отдельный каталог провайдеров и обязательную новую настройку не вводить.
4. После вопроса локально найти кандидатов, затем отобрать фрагменты. Поиск должен работать по значимым словам вопроса, а не искать всю естественную фразу как одну подстроку. Использовать текущий поиск и небольшую детерминированную обработку запроса. Морфологический и семантический поиск в первый выпуск не входят.
5. Начальные внутренние пределы: до 20 встреч-кандидатов, до 12 фрагментов суммарно, до 2 000 символов на фрагмент. При меньшем доступном контексте модели бюджет уменьшается. Кандидаты и короткая история диалога также не должны бесконтрольно расширять запрос. Настройки этих пределов пользователю не нужны.
6. Одна кнопка «Задать вопрос» запускает поиск и ответ; отдельное подтверждение каждого запроса не требуется. Использованные встречи показать вместе с ответом. Пользователь может исключить источник и повторить вопрос. При отсутствии совпадений предложить уточнить слова или область, не запускать ответ по пустым данным.
7. Для каждого фрагмента передать модели выданный приложением ID, название и дату встречи, тип текста и сам текст. Типы: расшифровка, summary, ручные заметки. Для фактов и цитат предпочитать расшифровку; выдержка из summary не выдаётся за дословную речь.
8. Если доступны одновременно summary и исходный текст, устаревший summary не использовать как актуальное подтверждение. Если доступен только такой summary, явно обозначить ограничение.
9. Модель отвечает только по переданным данным. Содержательные утверждения сопровождаются ссылками на фрагменты. При противоречии между встречами показать оба источника. Недостаток данных, исполнитель или срок не додумываются.
10. Приложение принимает только ID источников из текущего набора. Несуществующая ссылка не превращается в ссылку на случайную встречу; ответ с некорректными ссылками показывается с явной ошибкой проверки ссылок, без утверждения, что он проверен.
11. Нажатие на источник открывает встречу и выделяет соответствующий текст. Это работает без сохранённого аудио. При доступной и корректной привязке таймкода можно дополнительно воспроизвести запись существующим плеером.
12. При изменении исходного текста старая ссылка обозначается как устаревшая. Не выделять новый текст по старым номерам строк и не воспроизводить приблизительный участок аудио без надёжной привязки.
13. Поддержать уточняющие вопросы в текущем диалоге. Для вопросов вроде «А кто ответственный?» сохранить предыдущую тему и источники в ограниченном контексте; новый поиск учитывать выбранную область. История первого выпуска живёт в памяти до закрытия чата/приложения, это видно пользователю.
14. Добавить Stop, Retry и New chat. Ошибка сохраняет вопрос для повтора; незавершённый ответ обозначается как незавершённый. Поздний ответ не попадает в другой диалог или другую область поиска.

### Минимальный способ реализации

- Локальный поиск → ограниченный набор фрагментов → один запрос ответа к текущему LLM-backend. Отдельный запрос модели для планирования поиска и цикл вызова инструментов не нужны.
- Использовать транспорт и авторизацию существующих LLM-клиентов. Не прогонять архивный ответ через summary-шаблон с другой задачей.
- При нехватке контекста явно обозначить, что рассмотрена только выбранная часть результатов. Нельзя отвечать «во всём архиве этого не было» на основании первых 20 совпадений.
- Данные текстового источника: ID встречи, тип текста, версия содержимого и диапазон/якорь внутри этой версии. Индекс фрагментов строится на запрос, отдельная постоянно обновляемая база фрагментов не нужна.
- Диалог не получает инструментов записи, удаления, отправки сообщений, доступа к внешнему интернету или выполнения команд.
- Текст встречи передаётся как данные, а не инструкции. Проверка ID ссылок не является доказательством смысловой правильности ответа.
- В запрос уходят только выбранные фрагменты. Аудио, pairing-токены, полные логи Meet и ненужные контактные данные не отправляются. Тексты вопросов, ответов и фрагментов не пишутся в диагностику.
- Удалённая встреча исключается из поиска и будущего контекста; её прежние ссылки становятся недоступными. Нельзя доставать её из кэша для следующего ответа.

### Точки изменения

`DictationStore.searchMeetings` и чтение встречи; `MeetingsView`, `SearchResultsView`, `MeetingDetailView`; существующие LLM-клиенты; небольшой отдельный state/model чата по образцу `MeetingQuickActionModel`; открытие текстового источника и существующий `TranscriptRecordingSeek`.

### Приёмка

- В небольшом фикстурном архиве вопрос о релизе находит подходящие встречи в выбранной папке/периоде; удалённая и находящаяся за пределами области встреча не попадает в запрос.
- Ответ ссылается на переданные фрагменты; ссылка открывает нужный текст без аудио. Неизвестный ID и устаревшая версия обрабатываются явно.
- Пустой поиск, ограниченный набор результатов, отмена и ошибка провайдера не создают впечатления полного и подтверждённого ответа.
- Уточняющий вопрос сохраняет тему; смена области и New chat защищены от поздних результатов.
- Инструкция из текста встречи не даёт чату операции записи или выполнения команд.

## GM02. Понятная история обработки и безопасный повтор

### Уже есть у нас

- `MeetingRecord` хранит текущую расшифровку, исходный вариант текста, summary, ручные заметки, пути аудио, статус, ошибку summary и снимок шаблона.
- `MeetingProcessingStage` и `MeetingProcessingCard` показывают текущую стадию.
- `retranscribe(meeting:completion:)` повторно распознаёт сохранённое аудио; `resummarize(meeting:completion:)` отдельно обновляет summary.
- Существуют request gate для summary, сохранение аудио и восстановление прерванных записей.
- Полноценного сохраняемого журнала попыток с использованными моделями и источниками в проверенном `MeetingRecord` нет. `rawOriginalTranscript` не является историей всех попыток.

### Что берём у Gristmill

Разделение исходной записи, попытки обработки и результата. Видимые сбои и неполнота; повтор только нужного действия. Переносить систему эпох, калибровок, облачных ответов по каналам и весь worker не требуется.

Источник: [Recording and processing](https://github.com/timurkhakhalev/gristmill/blob/bbae52baa6b2b643740536a4a60f7a3f87cbb65e/.memory-bank/architecture/recording-processing.md).

### Добавить: поведение

1. В документе встречи добавить сворачиваемый блок «Обработка». Основная строка показывает происхождение текущих расшифровки и summary; ниже — попытки, новые сверху.
2. У попытки показывать действие, время, использованный backend/model, результат и понятную ошибку. Действия первого выпуска: первоначальная обработка, повтор ASR, повтор summary. Очистка и диаризация записываются как фактически выполненные стадии, если были включены.
3. Для ASR указать использованные источники: микрофон, системный трек, смешанная запись или импортированный файл. Модель и параметры фиксировать в момент запуска; последующее изменение настроек не меняет историю.
4. Не смешивать два состояния: завершилась ли обработка и полна ли исходная запись. Успешное распознавание неполного аудио остаётся результатом по неполному источнику.
5. Использовать уже известные ошибки захвата, восстановления и потерь чанков. Отсутствие ошибки или наличие двух файлов не доказывает полноту. Для старых записей без сведений показывать «Полнота неизвестна»; не придумывать пропущенные интервалы.
6. Сохранить отдельные действия «Повторить распознавание» и «Обновить summary». Кнопка повтора summary не запускает ASR. Если аудио удалено, ASR недоступен с причиной, но сохранённый текст остаётся пригоден для summary.
7. До успешного сохранения нового результата показывать предыдущий результат. Ошибка, отмена, пустой/непригодный ответ или отказ БД его не заменяют и не удаляют аудио.
8. Результат ASR и результат summary сохранять независимо. Если ASR удался, а summary нет, новый текст доступен; старый summary остаётся видимым с отметкой, что он относится к прежнему тексту.
9. Для одной встречи не запускать конкурирующие операции, способные перезаписать один результат. Использовать существующие task/request guards; не строить новую общую очередь. Отмена освобождает действие; позднее завершение не записывает устаревший результат.
10. Повторная обработка не стирает ручные заметки. Если generated summary редактируется пользователем, его замена должна быть явным действием с сохранением доступного текста при ошибке.
11. После перезапуска незавершённые попытки обозначать как прерванные. Не запускать незапрошенный повтор ASR/облачного LLM. Существующее восстановление аудио продолжает работать своим путём.
12. Удаление встречи удаляет журнал и метаданные. Очистка аудио сохраняет текст и историю обработки, но обновляет доступность повтора.

### Минимальные данные

Одна небольшая сущность попытки в существующем хранилище: ID, ID встречи, действие, начало/окончание, статус, последняя стадия, реально выбранные модели/параметры, использованные аудиоисточники или версия текста, предупреждения и безопасная ошибка.

Текущие поля `MeetingRecord` остаются основным результатом. Для расшифровки и summary сохраняется связь с успешной попыткой; summary также помнит версию входного содержимого.

- Сохранение результата, его версии и связи с успешной попыткой — одна транзакция.
- Журнал не дублирует аудио, транскрипты, промпты с пользовательским текстом и полные ответы провайдера.
- Одна строка соответствует пользовательской операции, внутренние транспортные ретраи отдельными строками не размножаются.
- Исторические успешные тексты не архивируются, откат к любой старой версии не входит в этот выпуск.
- Старым встречам не приписываются модели и попытки, которых приложение не записывало. Миграция не запускает обработку.

### Точки изменения

`StorageModels`, существующие миграции/`DictationStore`; запуск и завершение обработки в `GuesliController` и `MeetingSession`; `MeetingProcessingCard`/`MeetingDetailView`. Отдельные UI-статусы не должны менять протоколы аудиозахвата.

### Приёмка

- После изменения настроек история показывает модель, которой действительно получен результат.
- Сбой ASR, summary или сохранения в БД не уничтожает последний сохранённый результат и аудио.
- Сбой summary после удачного ASR оставляет новый текст и явно устаревший прежний summary.
- Успешная обработка известного неполного источника не убирает предупреждение.
- После перезапуска попытка обозначена прерванной, повтор не стартует сам.
- Повтор summary не вызывает ASR; отсутствие аудио не блокирует работу с текстом.

## GM03. Происхождение имён и актуальность summary

### Уже есть у нас

- Диаризация и `MeetingSession.speakerNameMap` связывают speaker ID с именами по наблюдениям Google Meet.
- `MeetSpeakerObservationLog` сохраняет наблюдения для встречи; повторное распознавание может использовать сохранённые данные bridge.
- Участники календаря хранятся отдельно.
- `MeetingSpeakerRename` меняет метки говорящего в строках расшифровки и валидирует имя.
- `renameMeetingSpeaker` сохраняет исправленный текст, оставляя исходную расшифровку и summary без изменений.
- В проверенном текущем представлении нет сохранённого источника каждого итогового имени и привязки summary к ревизии исправлений.

### Что берём у Gristmill

Имя — редактируемое предположение с происхождением. Ручное исправление имеет приоритет. После изменения имён существующий summary не переписывается молча, а получает отметку об устаревании.

Источник: [Platform speaker evidence](https://github.com/timurkhakhalev/gristmill/blob/bbae52baa6b2b643740536a4a60f7a3f87cbb65e/.memory-bank/architecture/speaker-evidence.md).

### Добавить: поведение

1. Рядом с именем показывать компактный источник: «Вручную», «Google Meet» или «Источник неизвестен». Для неназванного кластера остаётся «Говорящий N». В первом выпуске не добавлять неиспользуемые источники Voice/Zoom/Telemost/LLM.
2. «Google Meet» означает, что имя предложено по событиям платформы, а не что личность достоверно установлена. Не показывать проценты уверенности, которые не измерялись.
3. Переиспользовать текущий matcher. В этой задаче не менять его пороги и не строить новую систему доказательств. Если matcher не выбрал имя, источник не назначается.
4. Сохранять происхождение при присвоении имени вместе с результатом. При ручном исправлении заменить источник на «Вручную»; повторные автоматические события внутри той же версии текста его не перезаписывают.
5. Участник календаря — кандидат, а не доказательство, что он говорил. По одному факту наличия имени в календаре подпись не назначать.
6. Ручное переименование действует на конкретного говорящего внутри конкретной версии расшифровки, не на любой совпавший текст. Два разных speaker ID с одинаковым отображаемым именем остаются разными.
7. При повторном ASR кластеры могут измениться. Не переносить исправление `Speaker 1` в новый `Speaker 1` по совпадению номера. Предыдущая версия остаётся видимой до принятия нового результата; перед запуском предупредить, что имена может потребоваться назначить заново. Исправления прежней версии не выдавать за проверенные для новой.
8. После смыслового изменения имени существующий summary остаётся доступен и помечается: «Имена изменены после создания итога». Предложить «Обновить summary» или «Оставить как есть».
9. Новая генерация получает исправленные имена. Отметка снимается только после успешного сохранения summary для текущего содержимого. Ошибка генерации и исправление имён во время запроса не снимают её.
10. «Оставить как есть» скрывает предупреждение для текущей версии содержимого, не делает старый summary актуальным. Следующее исправление снова показывает предупреждение; чат GM01 по-прежнему знает, что summary устарел.
11. Старые встречи без записанного происхождения показывают неизвестный источник. Не восстанавливать его по внешнему виду имени. Ручное исправление старой встречи даёт известный источник только для исправленного говорящего.
12. Текстовый экспорт сохраняет итоговые имена и не включает сырые наблюдения Meet или контакты. CLI и интерфейс используют одну отображаемую расшифровку; существующий формат CLI не ломается.

### Минимальные данные

- Карта говорящих для конкретной версии транскрипта: ключ исходного speaker, отображаемое имя, источник и привязка к соответствующим репликам.
- В новой карте ID не зависит от отображаемого имени. При текущем строковом хранении допустима компактная аннотация реплик рядом с текстом; переход всей БД на новую модель транскриптов не требуется.
- Старый текст можно разбирать существующим парсером. При неоднозначных одинаковых метках нельзя обещать независимое исправление двух людей без исходной разметки; объяснить ограничение.
- Версия входного содержимого и версия, по которой создан summary, общие с GM02. Они учитывают замену транскрипта, изменение имён и используемых ручных заметок. Повторное сохранение того же значения версию не увеличивает.
- Исправление имени, обновлённый отображаемый текст и версия сохраняются атомарно. Сырые события bridge не переписываются.
- Во время миграции старого summary сведения о его входной версии неизвестны; не объявлять все старые summaries устаревшими без изменения пользователем. Первое последующее изменение отслеживается явно.

### Точки изменения

Выход `MeetingSession.speakerNameMap` и финальное форматирование текста; сохранение результата и переименование в `GuesliController`; `MeetingSpeakerRename`; `StorageModels`/`DictationStore`; имена и предупреждение в `MeetingDetailView`; формирование LLM-контекста и чтение текущей расшифровки через CLI.

### Приёмка

- Автоматическое имя Meet и ручное имя различимы после перезапуска.
- Автоматическое обновление не затирает ручное исправление; два новых говорящих с одинаковыми именами исправляются независимо.
- Замена транскрипта не переносит ручную личность по номеру кластера.
- Исправление имени сохраняет старый summary и показывает предупреждение. Неудачная или устаревшая генерация предупреждение не снимает.
- Старые данные читаются с неизвестным происхождением без выдуманных меток; экспорт не раскрывает сырые данные bridge.

## Порядок реализации и общая готовность

1. **GM02:** сохраняемые попытки, связь текущего результата с попыткой, версия входного содержимого и предупреждения о неполноте.
2. **GM03:** происхождение имён, приоритет ручных исправлений и актуальность summary на этой версии.
3. **GM01:** архивный чат использует уже актуальные тексты, имена, предупреждения и версии источников.

Каждый пункт можно поставлять отдельным изменением. До начала реализации не требуется отдельная исследовательская фаза.

Проверки реализации:
- Небольшие фикстуры поиска/ссылок, сохранности результата при сбое, миграции, источников имён и изменения данных во время запроса.
- Полный Swift suite: `swift test --package-path native/Guesli`.
- Ручная проверка области чата, перехода к тексту без аудио, повтора обработки и исправления имён.
- Проверки и модели используют временное хранилище, не пользовательский `~/Library/Application Support/Guesli/`.
- UI-ключи остаются English, русские строки добавляются в существующую feature-specific локализацию.
- Ни пользовательские тексты, ни имена, ни контактные данные не попадают в диагностические логи.
- При поставке приложения — каноническая production-сборка и проверка подписи/версии/свежего процесса по AGENTS.md. Наличие ТЗ, прохождение тестов и установленная рабочая версия — разные состояния готовности.

В этом ТЗ определены требуемое поведение и проверки. Реализация, запуск тестов, сборка и проверка приложения в рамках подготовки документа не выполняются.
